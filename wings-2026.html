Designing with Claude

Everything from the session in one place: the full class walkthrough, plus the people to reach out to when you want a second pair of eyes or another session.

Before You Start

Two decisions before you dive in

Work through these in order. The first tells you whether to loop in UX. The second tells you which tool to reach for.

Decision 1

Is the problem understood?

Not Yet → Work With UX

If you're still trying to understand the user problem, determine the right workflow, decide what should be built, or figure out which solution will create value, involve UX.

Yes → Move It Forward

If the problem and direction are already understood, Claude can help you move the work forward without waiting for UX to create every artifact or iteration.

Decision 2

What do I need to do?

Explore or Communicate → Claude Design

Visualize a defined change, explore variations, compare options, gather feedback, and communicate what the experience should be.

Work With the Implementation → Claude Code

Inspect components and code, understand implementation details, create handoff information, and work toward implementation.

💡 You may use one or both. A common flow: known problem → Claude Design → align on experience → Claude Code → implementation. If the experience is already established, a developer may start directly in Claude Code.
Try It Yourself

Claude Design + Claude Code

Practice making a small, defined product change with Claude Design, collaborating on that change, and then bringing it into Claude Code. Nothing here is gated - open the link, follow along, and reuse it as often as you need.

Part 1 · Start in Claude Design

Open Claude Design and set up your workspace

  1. Open the Claude application and select Design from the bottom-left navigation.
  2. Check the design system shown beneath the prompt field. If NiCE Brand is selected, change it to CXONE Official – Lyra Design System. NiCE Brand is intended for things like marketing and communications; Lyra contains the building blocks and standards intended for CXone product experiences.
  3. Open the practice dashboard below and make your own copy before editing. For this exercise, imagine it represents the current version of a real product.
💡 Using Lyra gives Claude a better starting point for product components, typography, spacing, colors, interaction patterns, and accessibility considerations. It doesn't mean everything Claude creates is automatically correct - you'll still need to review the result.
Open the practice dashboard
Part 2 · Make a Product Change

Add the ability to favorite a dashboard

Users may have dozens of dashboards, but typically return to the same few throughout the day. The team has already decided to let users favorite dashboards so they can quickly find the ones they use most.

🎯 Your task: add the ability to favorite a dashboard and view only your favorites.

Notice where we are in the decision model: is the problem understood? Yes. We know the problem and the direction the team wants to pursue. We're not asking Claude to decide what feature customers need - we're using Claude Design to explore and communicate how an already-defined feature could work.

  1. Prompt Claude to add the Favorites functionality. There isn't one correct prompt or a magic formula - describe what you want naturally and see what Claude creates. Try starting with only the requirement you've been given rather than specifying exactly what the interface should look like.
  2. Review what Claude decided. Don't assume the first result is correct just because it looks polished - compare it against the original requirement.
  3. Find at least one thing you'd change, tell Claude what you want corrected, and iterate. Claude isn't the decision-maker. You are.
  • Did it change only what I asked it to change?
  • Can I easily tell whether a dashboard is favorited?
  • Can I easily find just my favorites?
  • Does the change make sense for the user's task?
  • What decisions did Claude make that weren't actually in the requirement?
  • What happens when there aren't any favorites yet, or someone unfavorites an item while viewing only favorites?

You don't need to solve every one of these questions. The goal is to notice that Claude made decisions beyond what you explicitly told it - AI can make it much faster to create and change an artifact, but you still need to evaluate what it creates.

Part 3 · Compare Your Solution

Two people, one requirement, different results

If you're doing this exercise with someone else, compare your results. You both started with the same product and the same requirement: add the ability to favorite a dashboard and view only your favorites.

  • Did Claude give you the same solution?
  • Where did it put the Favorite action?
  • How did it represent the selected state?
  • How did it let you view your favorites?
  • Which decisions do you prefer, and why?

Two people can give Claude essentially the same requirement and receive different results. AI output isn't automatically "the design." It's something you can use to explore, discuss, and iterate.

Part 4 · Create a Tweak

Show today's experience next to Favorites

Now imagine Favorites is being considered for an upcoming release. You want to show someone the product as it exists today and then quickly show what changes when Favorites is included. That's where Tweaks can help.

  1. Open the Tweaks panel.
  2. Ask Claude to make the Favorites enhancement a Tweak.
  3. Once it's created, turn it on and off - now you have a simple way to communicate current experience versus Favorites enabled.
💡 Tweaks can also be useful for discussing feature scope, exploring variations, previewing combinations of proposed features, and showing how an experience might change across releases.
Open the Release Timeline Tweaks example
Part 5 · Collaborate

Bring others into the design

  1. Turn on Comment mode from the top bar and add a comment directly to an element of your design - for example, questioning the placement of the Favorite control or suggesting a different way to filter favorites.
  2. Comments let PMs, developers, designers, and other collaborators discuss a change in the context of the experience itself. Editors can respond, resolve comments, or ask Claude to apply feedback to the design.
  3. Use Share to send your work to someone else, ask them to review your Favorites experience and leave a comment, then use that feedback to iterate again.

The artifact you're creating can become a shared place for the team to discuss a defined product change, rather than simply being disposable AI output.

Part 6 · Notice When New Questions Appear

A "defined" requirement can still raise new questions

We started with what sounded like a defined requirement: let users favorite dashboards so they can quickly find the ones they use most. But working through the experience might uncover questions such as: are favorites personal to each user, or shared across a team?

Maybe your requirements already answer that. If they don't, Claude shouldn't quietly make that product decision for you. This doesn't necessarily mean you have to stop everything and call UX - it means you've discovered something that needs to be clarified with the right people. Sometimes you'll uncover a bigger question about the user's needs, workflow, or experience. That's when you may need to bring UX into the conversation.

💡 Using AI to move faster doesn't mean removing human judgment. Sometimes moving faster helps us discover the questions we still need to answer.
Part 7 · Move to Implementation

Send your design to Claude Code

Now imagine the team has reviewed the Favorites enhancement, answered the important questions, and agreed on the direction. We were exploring and communicating the experience in Claude Design - now we need to work with the implementation in Claude Code.

  1. From your Claude Design project, select Share.
  2. Select More formats and apps.
  3. Find Claude and select Send.
  4. Choose the appropriate options, then Copy prompt or Start session.
💡 Sending a design to Claude Code does not mean AI-generated code is automatically ready for production. Developers still own architecture, application state, business logic, APIs, testing, accessibility validation, code quality, code review, and integration into the actual product.
Part 8 · Explore the Implementation

Inspect what Claude Code created

  1. Explore the implementation: which components are being used, how the page is structured, how styles are applied, how the Favorite state is represented, how filtering works, and how your Tweak variation is represented.
  2. Ask Claude Code to explain which components the page uses.
  3. Ask Claude Code what components and states are needed to implement the Favorites feature, and to walk you through how the interaction is implemented.
  4. Ask Claude Code to create handoff documentation for the Favorites enhancement.

The value isn't simply that AI can produce code. Claude Code can also help you understand and work with the implementation.

What Happens Next

A typical workflow

Problem & direction understood → Claude Design - explore & communicate → Review - discover questions & iterate
Share + comment - PM, UX, Dev align → Claude Code - work with implementation → Developer integrates into the product → Normal testing, validation, review, release

You don't always need every step. If the experience is already established, a developer may start directly with Claude Code. And at any point, you may discover that the problem isn't actually as understood as you thought - that's useful. It tells you where more product or UX thinking is needed before moving forward.
