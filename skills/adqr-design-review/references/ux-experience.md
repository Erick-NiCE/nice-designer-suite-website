# UX Experience

Generated by `npm run gen:adqr-refs` from the rubric `score_design_review` reads. Never hand-edit. Rubric by Prafull Mane (ADQR).

Nielsen-style heuristics judged from the screens alone. Runs on every design, AI or not.

12 dimensions. Score each with exactly one band: 0, 2, 4, 6, 8 or 10.

## Flow `flow`

**Is the user journey logically structured and does each step move the user toward the intended outcome?**

| Band | Anchor |
| --- | --- |
| 0 | Steps are out of order in a way that blocks progress (e.g. asks to confirm before the data needed exists). |
| 2 | The sequence works but requires backtracking or redoing a step due to poor ordering. |
| 4 | The sequence is mostly workable, but at least one step lacks context or information it needed from a prior step. |
| 6 | Steps are in a sensible order with only minor friction — one step could reasonably move earlier. |
| 8 | Every step follows logically from the last, with no backtracking required. |
| 10 | The sequence is optimal — no step could be reordered to reduce friction or risk. |

Evaluate for:
- Prerequisites: completed before dependent actions
- Information dependency: needed information available before decisions
- Step sequence: arranged naturally
- Decision timing: sufficient context before decisions
- Action dependency: current action is possible based on prior steps
- Commitment timing: Save/Submit/Activate follows configuration/review
- Backtracking: poor sequencing does not force unnecessary return trips
- Progression: each step moves toward completion

Evidence to inspect: Screen sequence; Prototype navigation; Dependencies; User actions; State transitions.

Do **not** evaluate:
- Whether all requirements are represented — Flow Completeness
- Number of steps — Cognitive Load
- Label clarity — Clarity

## Clarity `clarity`

**Can users understand what the interface means, what they can do, and what happens next?**

| Band | Anchor |
| --- | --- |
| 0 | Labels, states, or values actively contradict each other or contradict the visible data (e.g. two fields disagree on the same fact). |
| 2 | A key label, action, or state is ambiguous enough that a reasonable user would misinterpret it. |
| 4 | At least one specific inconsistency exists (duplicate meaning shown two ways, a number that doesn't reconcile, an unlabeled value) but the screen is still usable. |
| 6 | Labels and states are understandable with only cosmetic issues (inconsistent casing, minor redundancy) that don't cause misinterpretation. |
| 8 | All labels, states, and next steps are clear and internally consistent, with no contradictions found. |
| 10 | Every label, value, and state is unambiguous and independently verifiable against the data shown. |

Evaluate for:
- Screen purpose
- Page/section titles
- Action labels
- Terminology
- Instructions
- System states
- Next-step expectations
- Ambiguous language

Evidence to inspect: Visible copy; Labels; CTAs; Messages; Titles; States.

Do **not** evaluate:
- Business correctness of terminology unless provided
- Brand voice unless specifically requested

## Interaction `interaction`

**Do controls and interactions behave in ways users can reasonably predict?**

| Band | Anchor |
| --- | --- |
| 0 | A control does something clearly contrary to its label or convention (e.g. "Cancel" appears to submit). |
| 2 | Primary and destructive actions aren't visually distinguished, risking accidental irreversible action. |
| 4 | Controls are recognizable but at least one lacks an expected state (no visible loading, no disabled state during a dependency). |
| 6 | Controls behave predictably with only minor gaps in secondary states not verifiable from a static view. |
| 8 | Every visible control's behavior matches convention, with clear primary/secondary/destructive differentiation. |
| 10 | Controls are unambiguous, appropriately differentiated, and show the states needed at each step (loading, success, error) where relevant. |

Evaluate for:
- Recognizable controls
- Expected behavior
- Primary/secondary/destructive visual differentiation
- Discoverability
- Loading behavior
- Success behavior
- Error behavior
- Disabled states where appropriate

Evidence to inspect: Controls; CTAs; Interactive states; Prototype behavior.

Do **not** evaluate:
- Code quality
- Actual interaction performance
- Accessibility implementation unless specifically visible
- Whether a destructive action can be confirmed, undone, or reversed — that's User Control & Freedom

## Information Architecture `information_architecture`

**Can users find, understand, and navigate the information they need?**

| Band | Anchor |
| --- | --- |
| 0 | Critical information needed for the current task is not present anywhere in what's shown. |
| 2 | Information exists but is grouped in a way that actively misleads (e.g. unrelated data placed under one heading). |
| 4 | Navigation or grouping is workable, but at least one important item is misplaced or hard to locate relative to related content. |
| 6 | Structure is logical with only minor prominence issues — an important item is present but not emphasized. |
| 8 | Grouping, hierarchy, and navigation all support finding what's needed without misplacement. |
| 10 | Structure is optimal — the most important information is the most prominent, and nothing needed is buried. |

Evaluate for:
- Logical grouping
- Hierarchy
- Navigation
- Information discoverability
- Related content proximity
- Categorization
- Labels supporting findability
- Important information prominence

Evidence to inspect: Navigation; Page structure; Sections; Menus; Information grouping.

Do **not** evaluate:
- Whether information itself is correct
- Backend data architecture

## Feedback & System State `feedback_system_state`

**Does the system keep the user informed about what is happening, what happened, and what happens next?**

| Band | Anchor |
| --- | --- |
| 0 | An action is available with no way to tell whether it succeeded, failed, or is still in progress. |
| 2 | Feedback exists for some actions, but the primary task has no confirmation of outcome. |
| 4 | Most actions have feedback, but timing or wording leaves real ambiguity about the current state. |
| 6 | Feedback covers before/during/after for the primary task, with only minor gaps on secondary actions. |
| 8 | Every visible action states what will happen, what's happening, and what happened, without ambiguity. |
| 10 | State is unambiguous at every step, including edge cases like partial failure or delayed effect. |

Evaluate for:
- Before action: user knows what will happen
- During action: user knows something is happening; progress/loading when needed
- After action: success/failure communicated
- Attention: important changes/alerts visible
- Next step: user knows what to do next

Evidence to inspect: Loading states; Success messages; Error states; Status indicators; Notifications; Progress indicators.

Do **not** evaluate:
- Actual system latency
- Backend reliability

## Error & Recovery `error_recovery`

**Can users prevent, understand, and recover from predictable errors?**

| Band | Anchor |
| --- | --- |
| 0 | An error condition is clearly reachable but nothing shown communicates it happened — no message, indicator, or visible change at all. |
| 2 | An error is shown, but its message doesn't say what went wrong or what to do next. |
| 4 | Errors are explained where shown, but at least one predictable error path (a required field, a failed submission) has no validation or handling at all. |
| 6 | Errors are validated and explained for the predictable cases, with only minor gaps (e.g. no retry offered, though the cause is clear). |
| 8 | Errors are prevented via validation where possible, and any shown are clearly explained with a visible recovery path. |
| 10 | Every predictable failure mode shown has prevention, a message explaining cause and fix, and an obvious way to recover or retry. |

Evaluate for:
- Error prevention via validation
- Error message clarity
- Error message explains the cause
- Error location
- Recovery or retry action
- Work preservation after a failure

Evidence to inspect: Forms; Validation; Error states; Recovery controls.

Do **not** evaluate:
- Actual backend error handling
- Error frequency in production
- Whether a destructive action is confirmed, undone, or reversible — that's User Control & Freedom

## User Control & Freedom `user_control_freedom`

**Can users exit, undo, or reverse an action rather than being forced forward?**

| Band | Anchor |
| --- | --- |
| 0 | A destructive or hard-to-reverse action executes immediately with no confirmation, undo, or way to reverse it. |
| 2 | A multi-step flow has no visible way to exit or cancel partway through — the only way out is finishing it. |
| 4 | An exit, cancel, or back control exists, but using it silently discards entered data with no warning. |
| 6 | Exit, cancel, and confirmation exist for the obvious cases, with only a minor gap (e.g. no undo after a completed action, though it was confirmed before running). |
| 8 | Every step offers a clear way to back out or cancel, and destructive actions are confirmed or undoable, with at most cosmetic gaps. |
| 10 | Users can exit, cancel, undo, or reverse every action shown, with no forced one-way paths and no silent data loss. |

Evaluate for:
- Exit or cancel available at every step
- Back navigation without losing entered data
- Undo after a completed action
- Confirmation before destructive or hard-to-reverse actions
- Escape from a multi-step flow without finishing it
- Warning before discarding entered data

Evidence to inspect: Cancel/Back controls; Confirmation dialogs; Undo controls; Multi-step wizards; Navigation away from an in-progress form.

Do **not** evaluate:
- Error message clarity or cause — that's Error & Recovery
- Whether an error occurred at all — that's Error & Recovery
- Visual distinction between primary/secondary/destructive controls — that's Interaction
- Screen density or number of steps — that's Cognitive Load

## Cognitive Load `cognitive_load`

**Does the experience require more mental effort than necessary to complete the task?**

| Band | Anchor |
| --- | --- |
| 0 | The user must track information across multiple screens or sections simultaneously with no way to see it in one place. |
| 2 | A single screen presents significantly more simultaneous decisions or fields than the task requires. |
| 4 | The screen is workable but has clear opportunities for progressive disclosure that aren't taken. |
| 6 | Information density is reasonable, with only minor unnecessary repetition or choice. |
| 8 | The task is broken into an appropriate number of decisions with no unnecessary density. |
| 10 | Only the information needed for the current decision is shown, in the simplest reasonable form. |

Evaluate for:
- Number of simultaneous decisions
- Information density
- Choice overload
- Repetitive input
- Memory burden
- Competing priorities
- Complex sequences
- Unnecessary information
- Progressive disclosure opportunities

Evidence to inspect: Screen density; Number of decisions; Form fields; Options; Instructions; Repeated actions.

Do **not** evaluate:
- User intelligence
- Whether advanced functionality should exist
- Business necessity of information

## Consistency `consistency`

**Is the experience internally consistent and predictable across the submitted journey?**

Excluded by the tool unless it needs 2 or more screens.

| Band | Anchor |
| --- | --- |
| 0 | The same action or state is represented in contradictory ways across screens (e.g. "Active" means different things on two screens). |
| 2 | A component or pattern changes meaning or behavior between screens without explanation. |
| 4 | Most patterns hold across screens, but at least one label, control, or status representation differs without reason. |
| 6 | Patterns are consistent with only cosmetic drift (casing, spacing) that doesn't change meaning. |
| 8 | Terminology, components, and interaction patterns match across every screen shown. |
| 10 | Every pattern, label, and state representation is identical in meaning and form everywhere it appears. |

Evaluate for:
- Terminology
- Component patterns
- Interaction patterns
- Navigation
- Button behavior
- Status representations
- Visual conventions
- Similar actions behaving similarly

Evidence to inspect: Screen A vs Screen B vs Screen C comparison; Controls; Labels; Interaction patterns.

Do **not** evaluate:
- Compliance with a design system unless rules are supplied
- Whether a pattern is aesthetically preferred

## Accessibility (WCAG) `accessibility_pour`

**Does the design appear to support an accessible experience, judged against WCAG's four principles (Perceivable, Operable, Understandable, Robust)?**

| Band | Anchor |
| --- | --- |
| 0 | Critical information is conveyed by color alone, or controls are unidentifiable as controls. |
| 2 | Text or controls appear low-contrast or ambiguous to the point that legibility is doubtful for many users. |
| 4 | Basics are met, but at least one POUR principle has a specific, visible gap (e.g. unclear focus order, a control with no visible label). |
| 6 | All four POUR principles are visibly addressed with only minor, non-blocking concerns. |
| 8 | Labels, contrast, and structure all appear to support an accessible experience with no visible gaps. |
| 10 | The design visibly anticipates accessibility needs beyond the minimum (e.g. redundant non-color cues, clear focus indicators). |

Evaluate for:
- Perceivable: readability, apparent contrast, non-color-dependent information, visual hierarchy, alternative representation where visually important
- Operable: identifiable controls, keyboard/focus considerations, logical interaction order, adequate target areas where visually assessable, no obvious inaccessible behavior
- Understandable: clear labels, instructions, errors, predictable behavior, understandable terminology
- Robust: semantic-looking controls, consistent control types, potential assistive-technology concerns, meaningful structure

Evidence to inspect: Screenshots; Visible states; Labels; Color usage; Interaction structure; HTML/DOM if supplied.

Do **not** evaluate:
- WCAG compliance claims
- Exact contrast ratio claims
- Keyboard compliance claims
- Screen-reader compatibility claims
- ARIA correctness claims without technical tooling

## Help & Documentation `help_documentation`

**When a task isn't self-explanatory, is guidance actually available at the point of need?**

| Band | Anchor |
| --- | --- |
| 0 | A control, field, or action whose purpose isn't inferable from its label alone (an unfamiliar icon, a jargon term, a multi-step configuration) has no explanation anywhere in what's shown. |
| 2 | Guidance for a non-obvious action exists somewhere, but not where the action is — e.g. a general help link elsewhere, with nothing next to the actual control. |
| 4 | Most non-obvious actions have some in-context guidance, but at least one comparably complex one has none. |
| 6 | Every non-obvious action has in-context guidance, but at least one is a bare icon or generic link with no visible explanatory text. |
| 8 | Every non-obvious action has specific, in-context guidance that explains what to do, with only minor room to be more concrete. |
| 10 | Guidance appears exactly where a task isn't self-explanatory, is specific enough to act on immediately, and isn't added where the interface is already self-evident. |

Evaluate for:
- Non-obvious or jargon terms explained
- Complex or multi-step actions supported by a hint or example
- Unfamiliar icons or controls labeled or explained
- Guidance placed next to the action it explains, not buried elsewhere
- Placeholder or example text for ambiguous input fields
- Links to further explanation where a task is genuinely complex

Evidence to inspect: Tooltips; Inline hints; Placeholder text; Help or info icons; Example values; Links to documentation; First-use guidance.

Do **not** evaluate:
- Whether existing labels are ambiguous — that's Clarity
- Error message quality — that's Error & Recovery
- Screen information density — that's Cognitive Load
- Whether help documentation exists outside what's shown (a help center not visible in these screens)

## Flexibility and Efficiency of Use `flexibility_efficiency`

**For a repeat or experienced user, is there a faster path through a frequent task than the full step-by-step default?**

Excluded by the tool unless it needs a semi- or fully interactive input.

| Band | Anchor |
| --- | --- |
| 0 | A frequent, repeatable action (e.g. adding another of the same item) has no faster path than repeating the entire multi-step flow from the start every time. |
| 2 | A shortcut or accelerator exists but is effectively undiscoverable (no visible affordance, buried placement) so a real user would default to the slow path anyway. |
| 4 | One accelerator is visible (e.g. a duplicate action, a saved preset, a keyboard-shortcut hint) but another clearly repeatable action in the same flow has none. |
| 6 | Accelerators cover the most frequent repeatable action shown, with only a minor gap on a secondary one. |
| 8 | Every clearly repeatable action shown has a visible faster path (bulk action, saved default, shortcut, recent-choice recall) alongside the full manual one. |
| 10 | The design actively offers the faster path as the default for a repeat user (e.g. pre-filled from last-used values) while still leaving the full manual path available. |

Evaluate for:
- Bulk or batch actions for repeated items
- Keyboard shortcuts or accelerator hints
- Saved presets, templates, or defaults from prior use
- Ability to duplicate or repeat a prior configuration
- Recently-used values offered instead of starting blank
- Shortcuts genuinely discoverable, not just technically present

Evidence to inspect: Bulk/multi-select controls; Keyboard shortcut hints; Saved filters or presets; Duplicate/repeat actions; Recently used lists; Default values pre-filled from context.

Do **not** evaluate:
- Whether the basic single-item flow works at all — that's Flow or Interaction
- Actual keyboard-shortcut implementation correctness
- Screen density — that's Cognitive Load
- Whether shortcuts are documented — that's Help & Documentation
